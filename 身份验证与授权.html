    8. 身份验证与授权

    每个请求都会引出两个不同的问题：

    • 用户是谁？这就是身份验证：用户已使用用户名和密码表明身份，之后的每个请求都必须证明它来自该用户；
    • 他们有权访问此页面吗？这就是授权：在案例研究中，只有角色为 ADMIN 的用户才能管理医生和客户。

    身份证明必须随每个请求一起提交。[Symfony] 通常把已登录的用户存储在它的会话 中（参见作用域一节），这是 Web 应用程序最简单的解决方案。而案例研究在其所有版本（[ASP.NET Core MVC]、[Spring MVC]、[NestJS]、[Flask]、[Laravel]）中，改为使用令牌 （JWT，JSON Web Token），我们这里也将使用它：登录后，服务器生成一个包含用户身份的令牌，并用密钥对其进行签名（这就是示例 23 中签名 Cookie 背后的原理）。令牌存储在 Cookie 中；浏览器在每个请求中把它发回；服务器验证签名。用户可以读取自己的令牌，但不能修改它：任何修改都会使签名失效。其格式是标准化的（RFC 7519），所有编程语言都能理解，并且令牌包含其过期日期。最重要的是，服务器无需存储任何内容：任何知道密钥的服务器都可以验证令牌。

    [Symfony] 拥有一个全面的安全组件，由 SecurityBundle 集成，我们将原样使用其中的各个元素：

    • 应用程序的 URL 分布在各个防火墙 （firewalls）中，每个防火墙都有自己的用户身份验证方法；
    • 身份验证由认证器 （authenticators）处理：这些对象为每个请求确定用户的身份。[Symfony] 提供了其中的几种（登录表单、会话、API 令牌等）；我们将编写自己的认证器，它读取 JWT 令牌。应用程序的其余部分只看到结果：已通过身份验证的用户，由 [#[CurrentUser]]、[$this->getUser()] 提供，在视图中则由 [app.user] 提供；
    • 用户由用户提供者提供，其密码由 PasswordHasher 组件进行哈希处理（算法 [bcrypt]）；
    • 授权是基于角色的：页面保护由访问控制规则（[access_control]）或动作的 [#[IsGranted]] 属性来描述；视图使用 [is_granted] 检查权限；
    • 登录尝试次数由 RateLimiter 组件限制（示例 27）。

    所有这些都由内核事件监听器完成（上一章）：防火墙监听 [kernel.request] （优先级 8），[#[IsGranted]] 在 [kernel.controller_arguments] 上被读取，而拒绝访问是异常，在 [kernel.exception] 上处理。

    令牌的生成和验证由 [firebase/php-jwt] 库处理，它是 [PHP] 中最常用的 JWT 库，由示例中的 [composer.json] 文件安装。（有一个广泛使用的令牌 Bundle——JWT 和 [LexikJWTAuthenticationBundle]——专为 API 设计；对于 Web 应用程序，只需几行代码就足够了，而且它们能更好地说明这一机制。）

    1

php -d variables_order=EGPCS -S localhost:8000 -t public

    • 第 9–11 行：用户提供者——根据用户 ID 查找用户的服务（这里是我们的类 [UsersService]）。[Symfony] 提供了几种：[memory] （写在此文件中的列表）、[entity] （数据库表；见案例研究）等；

namespace App\Security;

use Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface;
use Symfony\Component\Security\Core\User\UserInterface;

readonly class User implements UserInterface, PasswordAuthenticatedUserInterface
{
    public function __construct(
        public string $login,
        public string $name,
        // 角色：USER 或 ADMIN
        public string $role,
        // 密码的哈希（对于从令牌读取的用户则为空）

        return $this->login;
    }

    // 角色，按 Symfony 的含义：以 ROLE_ 开头的字符串
    public function getRoles(): array
    {
        return ['ROLE_'.$this->role];
    }

    public function getPassword(): string
    {
        return $this->passwordHash;
    }
}
    • 第 11 行：一个用户。[Symfony] 要求已认证用户实现 [UserInterface] 接口：通过其方法获取用户的 ID 和角色。[PasswordAuthenticatedUserInterface] 接口则增加了哈希密码。在典型的应用程序中，用户表对应的 [Doctrine] 实体（下一章）会实现这些方法；
    • 第 13–23 行：登录名、姓名、角色、密码哈希，以及验证该用户身份的令牌内容（对于从用户列表中取得的用户，该项为空）。服务器绝不存储密码，即使是加密形式也不行：如果数据库被盗，密码也会随之被盗（而且很多人在所有地方都使用同一个密码）。它存储的是哈希函数的结果，哈希函数是一种单向函数：你可以计算出密码的哈希值，但无法从哈希值还原出密码。要验证输入的密码，只需计算其哈希值并与存档的哈希值比较；

    <?php
// src/Security/UsersService.php：用户，存放在内存中（示例 28
// 和案例研究会把它们放入数据库）。UserProviderInterface：按 Symfony 的含义，
// 是用户提供者（PROVIDER）（见 config/packages/security.yaml）

namespace App\Security;

use Symfony\Component\Security\Core\Exception\UnsupportedUserException;
use Symfony\Component\Security\Core\Exception\UserNotFoundException;
use Symfony\Component\Security\Core\User\UserInterface;
use Symfony\Component\Security\Core\User\UserProviderInterface;

class UsersService implements UserProviderInterface
{
    // 我们绝不保存密码，只保存其 bcrypt 哈希，它由以下命令
    // 一次性计算得出：php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const USERS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],
        'admin' => ['Administrator', 'ADMIN', '$2y$10$m5o9euCi0EdgoZkLVw.UsO58RxJcqhMBfVrlLMCIOh2LyGSjuN29K'],
    ];

    public function find(string $login): ?User
    {
        if (! isset(self::USERS[$login])) {
            return null;
        }
        [$name, $role, $hash] = self::USERS[$login];
        return new User($login, $name, $role, $hash);
    }

    // UserProviderInterface 的三个方法
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        return $this->find($identifier) ?? throw new UserNotFoundException();
    }

    // 存储在会话中、用于重新加载的用户：这里从不调用，
    // 因为防火墙是无状态的
    public function refreshUser(UserInterface $user): UserInterface
    {
        throw new UnsupportedUserException();
    }

    public function supportsClass(string $class): bool
    {
        return $class === User::class;
    }
}
    • 第 17–20 行：两个硬编码的测试用户（示例 28 和案例研究会把它们存储在数据库中）：每个登录名对应姓名、角色和密码哈希。哈希使用 bcrypt 算法生成，该算法专为密码设计。它有两个显著特点。它被有意设计得慢，且慢的程度可调（cost，此处设为 10：2^10 个计算周期，体现在哈希中的 [$10$]）：只需几十毫秒，用户察觉不到，但会让黑客尝试数十亿个密码的代价极其高昂。它还会加盐：哈希之前，会把随机生成的盐值 与密码混合，并存储在哈希本身之中（即 [$10$] 之后的 22 个字符）；因此，两个密码相同的用户会得到不同的哈希。这些哈希是一次性计算好的，使用 [password_hash] 函数（来自 [PHP] ，第 16 行），或使用 [bin/console security:hash-password] 命令（来自 [Symfony]）：由于应用程序在每次请求时都会重新构建，每次请求都重新计算会白白浪费时间。[bcrypt] 只考虑密码的前 72 个字节：案例研究对此做了处理；
    • 第 22–29 行：某个登录名对应的用户，或 [null]。[isset] 检查某个键是否存在；赋值 [[$name, $role, $hash] = ...] 对数组进行解构：每个变量接收对应的元素；
    • 第 32–47 行：[UserProviderInterface] 接口的三个方法，它们使该类成为用户提供者：[loadUserByIdentifier] 返回与某个标识符关联的用户，或抛出 [UserNotFoundException] 异常；[refreshUser] 重新加载存储在会话中的用户（对于无状态防火墙则不需要）；[supportsClass] 指明所提供用户的类。当左侧表达式的计算结果为 [??] 时，运算符 [throw] 会抛出异常，其后跟随 [null]。

    <?php
// src/Security/AuthService.php：密码和 JWT 令牌的检查

namespace App\Security;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;
use Throwable;

class AuthService
{
    // 携带令牌的 Cookie 的名称
    public const COOKIE = 'token';

    public function __construct(
        private UsersService $users,
        // 密码哈希服务（见 config/packages/security.yaml）
        private UserPasswordHasherInterface $hasher,
        // #[Autowire(env: ...)]：环境变量的值（.env 文件）；
        // int: 前缀将其转换为整数
        #[Autowire(env: 'JWT_SECRET')] private string $secret,
        #[Autowire(env: 'int:JWT_DURATION_MINUTES')] public readonly int $durationMinutes,
    ) {
    }

    // 用户，如果登录名未知或密码错误则为 null。
    // isPasswordValid 使用已存储哈希的盐值对输入的密码进行哈希，
    // 然后比较两个结果
    public function validate(?string $login, ?string $password): ?User
    {
        if (! $login || $password === null) {
            return null;
        }
        $user = $this->users->find($login);
        if ($user === null || ! $this->hasher->isPasswordValid($user, $password)) {
            return null;
        }
        return $user;
    }

    // 用户的 JWT 令牌，使用密钥签名（HMAC-SHA256）
    public function createToken(User $user): string
    {
        $now = time();
        // 令牌的内容：“claims”（关于用户的声明）
        $claims = [
            'sub' => $user->login,
            'name' => $user->name,
            'role' => $user->role,
            'iat' => $now,
            'exp' => $now + $this->durationMinutes * 60,
        ];
        return JWT::encode($claims, $this->secret, 'HS256');
    }

    // 由签名和过期日期
    // 均有效的令牌所描述的用户；否则为 null（伪造的、过期的或无法读取的令牌）
    public function check(string $token): ?User
    {
        try {
            // decode 返回一个对象；(array) 将其转换为关联数组
            $claims = (array) JWT::decode($token, new Key($this->secret, 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new User($claims['sub'], $claims['name'], $claims['role'], claims: $claims);
    }
}
    • 第 17–26 行：该服务接收用户提供者、密码哈希服务（[UserPasswordHasherInterface]，应用在 [security.yaml] 中选定的算法）以及两个配置值。属性 [#[Autowire(env: 'NAME')]] 提供某个环境变量的值；前缀可对其进行转换：[int:] 转换为整数（还有其他前缀：[bool:]、[json:]、[base64:]等）。有效期是一个只读的公共属性：控制器会使用它；
    • 第 31–41 行：验证用户名和密码。[isPasswordValid] 使用存储的哈希盐值对输入的密码进行哈希，并比较两个哈希值。未知的用户名和错误的密码会得到相同的结果，即 [null]；
    • 第 44–56 行：令牌生成。令牌包含一个关于用户的声明数组（claims）。其中一些有标准化的名称：[sub] （subject），即用户 ID；[iat] （issued at），即创建日期；[exp] （expiration），即过期日期。日期以自 1970 年 1 月 1 日以来经过的秒数表示（[time()] 函数，来自 [PHP]）。其他字段是可选的：此处为姓名和角色。[JWT::encode] 生成令牌，并使用 [HS256] 算法对其签名（HMAC-SHA256，一种使用共享密钥的签名）；
    • 第 60–69 行：令牌验证。[JWT::decode] 验证签名和过期日期，然后返回声明（一个对象，由 [(array)] 转换为数组）。任何异常（伪造、过期或格式错误的令牌）都会引发异常；[catch (Throwable)] 会捕获所有异常（[Throwable] 是 [PHP] 中所有异常和错误的接口；当变量不被使用时，变量名可以省略）。[Key] 对象将密钥与一种算法关联起来：如果令牌指定了不同的算法（或根本没有指定，即 [none]），就会被拒绝。有效的令牌会变成一个没有哈希的 [User]，连同它的声明（名为 [claims] 的参数）。

// src/Security/TokenAuthenticator.php：防火墙的身份验证器（AUTHENTICATOR）（见
// config/packages/security.yaml）：在每次请求时，它根据 [token] Cookie 中的
// JWT 令牌确定用户是谁

namespace App\Security;

use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Exception\AuthenticationException;
use Symfony\Component\Security\Core\Exception\CustomUserMessageAuthenticationException;
use Symfony\Component\Security\Http\Authenticator\AbstractAuthenticator;
use Symfony\Component\Security\Http\Authenticator\Passport\Badge\UserBadge;
use Symfony\Component\Security\Http\Authenticator\Passport\Passport;
use Symfony\Component\Security\Http\Authenticator\Passport\SelfValidatingPassport;
use Symfony\Component\Security\Http\EntryPoint\AuthenticationEntryPointInterface;

class TokenAuthenticator extends AbstractAuthenticator implements AuthenticationEntryPointInterface
{
    public function __construct(private AuthService $auth)
    {
    }

    // 仅当请求携带令牌 Cookie 时，身份验证器才会起作用；
    // 否则，访问者仍然是匿名的
    public function supports(Request $request): ?bool
    {
        return $request->cookies->has(AuthService::COOKIE);
    }

    // 用户的通行证（PASSPORT）：他们是谁（徽章），以及如何检查。
    // 令牌已经检查过：通行证自行验证（SelfValidatingPassport）
    public function authenticate(Request $request): Passport
    {
        $user = $this->auth->check($request->cookies->get(AuthService::COOKIE));
        if ($user === null) {
            throw new CustomUserMessageAuthenticationException('invalid token');
        }
        // 徽章：登录名，以及返回用户的函数（这里是令牌中的
        // 用户，无需查询用户列表）
        return new SelfValidatingPassport(new UserBadge($user->login, fn () => $user));
    }

    // 有效的令牌：null，请求继续前往操作
    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null;
    }

    // 无效的令牌（过期、伪造）：转到 /login，并删除 Cookie
    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        $response = new RedirectResponse('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // 入口点（ENTRY POINT）：对请求受保护页面的匿名访问者给出的
    // 响应；这里是重定向到登录页面
    public function start(Request $request, ?AuthenticationException $authException = null): Response
    {
        return new RedirectResponse('/login');
    }
}

    对于每个通过防火墙的请求，[Symfony] 会按以下顺序调用认证器的方法：

    • 第 28–31 行：[supports]：认证器是否参与此请求？如果请求包含令牌 Cookie，则参与。否则什么也不会发生：访问者仍然是匿名的；
    • 第 35–44 行：[authenticate] 构造一个通行证：用户的身份（一个徽章，[UserBadge]），以及要验证的凭据。标准登录表单会把输入的密码放入通行证中，由 [Symfony] 自行验证。这里的凭据是令牌，已经由 [AuthService] 验证过：通行证自行验证（[SelfValidatingPassport]）。徽章包含登录名和一个用于识别用户的函数：在本例中，就是令牌所描述的用户，无需查询用户列表（如果没有这个函数，[Symfony] 就会向提供者请求用户）。无效的令牌会引发身份验证异常；
    • 第 47–50 行：[onAuthenticationSuccess]：身份验证成功。返回 [null] 会让请求带着已认证的用户继续进入操作。（登录表单在此处会重定向到主页）；
    • 第 53–58 行：[onAuthenticationFailure]：身份验证失败（令牌过期或被伪造）。响应会重定向到登录页，并顺便清除 Cookie：[clearCookie] 会向响应中添加一个空的、已过期的 Cookie；
    • 第 62–65 行：[start] 是 [AuthenticationEntryPointInterface] 接口的方法：防火墙的入口点，即发送给请求受保护页面的匿名访问者的响应。在本例中，是重定向到登录页。

    认证器不拒绝访问：它判定用户是谁，或者判定用户是匿名的。这就是身份验证。拒绝访问由访问控制负责。

// src/Controller/AuthController.php：登录和注销

namespace App\Controller;

use App\Security\AuthService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    public function __construct(private AuthService $auth)
    {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->render('auth/login.html.twig');
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        // 表单的防 CSRF 令牌（见示例 21）
        if (! $this->isCsrfTokenValid('login', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $request->getPayload()->getString('login');
        $user = $this->auth->validate($login, $request->getPayload()->getString('password'));
        if ($user === null) {
            // 故意含糊的消息：我们不说明是登录名还是密码有误
            return $this->render('auth/login.html.twig', ['login' => $login,
                'error' => 'Incorrect login or password.']);
        }
        // Cookie 中的令牌：页面的 JavaScript 无法读取它
        // （httpOnly）；它不会随来自其他站点的 POST 请求一起发送
        // （sameSite）；它会在令牌过期的同时消失
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    // 注销：仅限 POST（放在另一个站点上的简单链接，无法
    // 在用户不知情的情况下使其注销）；我们删除 Cookie
    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }
}
    • 第 36–38 行：登录表单与所有表单一样，受到防伪造请求的保护（示例 21）；
    • 第 40–45 行：登录流程。如果失败，表单会连同输入的用户名和一条故意含糊的消息重新显示：如果说“用户名未知”，就会向黑客泄露哪些用户名是存在的；
    • 第 49–54 行：如果成功，令牌会存储在 Cookie 中，并将用户重定向到受保护的页面（PRG 模式）。该 Cookie 是 [httpOnly] 的：页面的 [JavaScript] 无法读取它，从而保护令牌免受脚本注入（XSS）；它是 [SameSite=Lax] 的：浏览器不会在源自其他站点的 POST 请求中发送它，从而保护应用程序免受 CSRF 攻击；它的过期日期（[withExpires]，此处为自 1970 年以来的秒数）与令牌的相同。在生产环境中使用 HTTPS 时，我们还会添加 [withSecure(true)]：该 Cookie 绝不会通过未加密的连接发送；
    • 第 59–68 行：注销会删除 Cookie（[clearCookie]）。这是一个受防 CSRF 令牌保护的 POST 操作：放在其他站点或图片中的指向 [/logout] 的简单链接，无法在用户不知情的情况下让其注销。请注意令牌的一个局限：令牌本身在过期前一直有效。拿到其副本的人仍然可以使用它。这就是要限制其有效期的原因。

// src/Security/CaptchaService.php：待处理的验证码，由服务器保存在
// 缓存中（见示例 20）

namespace App\Security;

use Psr\Cache\CacheItemPoolInterface;

class CaptchaService
{
    // 验证码的有效期，以秒为单位
    private const LIFETIME = 600;

    public function __construct(private CacheItemPoolInterface $cache)
    {
    }

    public function generate(): Captcha
    {
        $text = CaptchaDrawing::randomText(5);
        // 一个无法猜测的随机标识符：由加密生成器（random_bytes）生成的
        // 12 个字节，以十六进制（bin2hex）写出
        $id = bin2hex(random_bytes(12));
        // 缓存中的预期答案，保存 10 分钟（expiresAfter）：
        // 之后缓存会自行将其遗忘
        $item = $this->cache->getItem("captcha.$id");
        $this->cache->save($item->set($text)->expiresAfter(self::LIFETIME));
        return new Captcha($id, CaptchaDrawing::svg($text));
    }

    // 验证码在任何情况下都会被消耗：一张图像只使用一次
    public function check(?string $id, ?string $answer): bool
    {
        // 格式错误的标识符不能作为缓存的键
        if ($id === null || ! ctype_xdigit($id) || $answer === null) {
            return false;
        }
        $item = $this->cache->getItem("captcha.$id");
        // deleteItem：无论答案是否正确，都会从缓存中删除该答案
        $this->cache->deleteItem("captcha.$id");
        if (! $item->isHit()) {
            return false;    // 未知的标识符，或已过期的验证码
        }
        // strcasecmp 对两个相等的字符串返回 0，不区分大小写
        return strcasecmp($item->get(), trim($answer)) === 0;
    }
}
    • 第 18–29 行：一个新的验证码：随机文本、随机且无法猜测的标识符，以及图片。对于每个标识符，服务器会把预期的答案在缓存中存储十分钟（示例 20）：缓存项的 [expiresAfter] 方法以秒为单位设置其生存期。超过这个时间后，缓存会自动丢弃它。页面只会收到标识符和图片：答案绝不会离开服务器；
    • 第 32–46 行：验证。标识符来自客户端：我们首先验证它是否由十六进制数字组成（[ctype_xdigit]），因为某些字符（[{}()/\@:]）在缓存键中是禁止使用的，使用它们会抛出异常。读取该缓存项后，将其从缓存中移除（[deleteItem]）：无论成功与否，验证码在所有情况下都会被消耗。否则，程序就可以对同一张图片尝试所有可能的答案。比较时忽略大小写（[strcasecmp] 对于两个相同的字符串返回 0，不区分大写和小写字母）以及输入两侧的空格（[trim]）。

// src/Controller/AuthController.php：登录（带验证码和尝试
// 次数限制）和注销

namespace App\Controller;

use App\Security\AuthService;
use App\Security\CaptchaService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\RateLimiter\RateLimiterFactoryInterface;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    // $loginLimiter：[login] 限制器的工厂（见 config/packages/framework.yaml）；
    // 参数的名称指明了所用的限制器
    public function __construct(
        private AuthService $auth,
        private CaptchaService $captchas,
        private RateLimiterFactoryInterface $loginLimiter,
    ) {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->loginPage();
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        $inputs = $request->getPayload();
        if (! $this->isCsrfTokenValid('login', $inputs->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $inputs->getString('login');
        // 此客户端的限制器：其失败计数器的键是它的 IP 地址
        $limiter = $this->loginLimiter->create($request->getClientIp());

        // 1. 被阻止的地址甚至不会被处理；consume(0) 查看
        // 计数器，但不消耗任何内容
        $state = $limiter->consume(0);
        if ($state->getRemainingTokens() === 0) {
            $seconds = $state->getRetryAfter()->getTimestamp() - time();
            return $this->loginPage($login, "Too many attempts: try again in $seconds s.");
        }
        // 2. 先验证验证码（开销小），再验证密码（bcrypt，开销大）；
        // consume()：再记一次失败
        if (! $this->captchas->check($inputs->getString('captchaId'), $inputs->getString('captcha'))) {
            $limiter->consume();
            return $this->loginPage($login, 'The image code is incorrect.');
        }
        $user = $this->auth->validate($login, $inputs->getString('password'));
        if ($user === null) {
            $limiter->consume();
            return $this->loginPage($login, 'Incorrect login or password.');
        }
        // 登录成功会清除失败记录
        $limiter->reset();
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // 每次显示表单都会生成一个新的验证码
    private function loginPage(?string $login = null, ?string $error = null): Response
    {
        return $this->render('auth/login.html.twig', ['login' => $login, 'error' => $error,
            'captcha' => $this->captchas->generate()]);
    }
}
    • 第 21–26 行：控制器接收限制器 [login] 的工厂；
    • 第 49 行：该客户端的限制器 [create(key)] 返回一个在此键下拥有独立计数器的限制器——在本例中，键是客户端的 IP 地址（[getClientIp()]）；
    • 第 53–57 行：被封锁的地址甚至不会被理会。[consume(0)] 在不消耗任何令牌的情况下查询限制器；它返回的 [RateLimit] 对象提供剩余令牌数（[getRemainingTokens()]）以及该操作再次被允许的日期（[getRetryAfter()]），由此可以推算出需要等待的秒数；
    • 第 60–68 行：验证码在密码之前验证；验证验证码几乎没有成本，而 [bcrypt] 则是有意设计得很慢。因此，输入错误验证码的程序不会触发 [bcrypt]。每次失败（无论是验证码错误还是密码错误）都会消耗一个令牌（[consume()]，默认消耗一个）。第三次失败后，不再有剩余令牌：该地址会被封锁，直到 60 秒窗口结束，窗口从第一次失败开始计算；
    • 第 70 行：登录成功会清除失败的尝试记录（[reset()]）；
    • 第 91–95 行：每次显示表单时，都会生成一个新的验证码，即使是在尝试失败之后。

    SecurityBundle 还提供了内置的登录限制（[login_throttling] 防火墙选项），它适用于其自带的登录认证器（[form_login]等），而不适用于我们的操作。要限制某个路由的请求数量，我们可以以同样的方式使用限制器，既可以放在操作内部，也可以放在 [kernel.request] 的监听器中。我们选择只统计失败的尝试，以免给正常登录的用户造成不便。
