    3. 动作模型

    动作需要浏览器发送的信息：URL 的参数（[?name=martin&age=42]）、表单字段、JSON 请求正文，有时还有一个 HTTP 请求头。本课程把所有这些信息统称为动作模型。本章展示 [Symfony] 动作如何获取这些信息、把它们转换为正确的类型并验证它们。这个过程称为数据绑定。

    [Symfony] 通过 [Request] 对象（示例 05）提供对请求信息的访问，以字符串的形式，并附带一些转换方法。它还可以绑定 这些信息到动作的参数上，方法是使用属性（[#[MapQueryParameter]]、[#[MapQueryString]]、[#[MapRequestPayload]]），并验证它，使用的是其 Validator 组件：我们用约束 （“必填”“0 到 150 之间的整数”等）来描述期望的数据，这些约束写成 [PHP] 属性之类的形式，由验证器检查数据是否符合它们。我们先手工读取参数（示例 07），然后让框架负责它们的转换和验证（示例 08 至 12）。在下一章中，同样的约束将用来验证 HTML 表单。

    请注意术语：在下一章中，“模型”一词主要指动作传递给其视图的数据。本章中所用的动作模型，则是它所接收的数据。

    示例 07 至 12 的运行方式与上一章的示例相同：打开到示例文件夹的终端，[php -S localhost:8000 -t public]；[Ctrl-C] 关闭服务器。大多数示例使用示例 03 中的监听器 [ReadableJson] ，从而得到可读的 JSON。我们只会在它们的配置文件引入新内容时才加以说明。

    <?php
// src/Controller/ParametersController.php：URL 的参数（“查询字符串”）

namespace App\Controller;

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\MapQueryParameter;
use Symfony\Component\HttpKernel\Exception\BadRequestHttpException;
use Symfony\Component\Routing\Attribute\Route;

#[Route('/parameters', name: 'parameters_', methods: ['GET'])]
class ParametersController extends AbstractController
{
    // /parameters/action01?name=martin：$request->query 包含
    // URL 的参数；get 返回参数的值，如果缺失则返回 null
    #[Route('/action01', name: 'action01')]
    public function action01(Request $request): Response
    {
        $name = $request->query->get('name');
        return new Response("name = [$name], of type ".get_debug_type($name));
    }

    // /parameters/action02?age=42：getInt 将值（字符串）转换为
    // 整数；缺失的参数得到 0，不是整数的值则会产生
    // 400 错误
    #[Route('/action02', name: 'action02')]
    public function action02(Request $request): Response
    {
        $age = $request->query->getInt('age');
        return new Response("age = [$age], of type ".get_debug_type($age));
    }

    // /parameters/action03?age=42：必需的参数，手动转换；
    // 缺失或不是整数的值会产生 400 响应
    #[Route('/action03', name: 'action03')]
    public function action03(Request $request): Response
    {
        $text = $request->query->get('age');
        if ($text === null) {
            // 一个 HTTP 异常：Symfony 会将其转换为 400 响应（Bad Request）
            throw new BadRequestHttpException('the [age] parameter is required');
        }
        // filter_var 返回字符串中包含的整数，或者 false
        $age = filter_var($text, FILTER_VALIDATE_INT);
        if ($age === false) {
            throw new BadRequestHttpException("[$text] is not an integer");
        }
        return new Response("age = [$age], of type ".get_debug_type($age));
    }

    // /parameters/action04?page=2：参数缺失时使用默认值
    #[Route('/action04', name: 'action04')]
    public function action04(Request $request): Response
    {
        $page = $request->query->getInt('page', 1);
        return new Response("page = [$page]");
    }

    // /parameters/action05?q=symfony：URL 参数的名称不一定与
    // PHP 变量的名称相同
    #[Route('/action05', name: 'action05')]
    public function action05(Request $request): Response
    {
        $search = $request->query->get('q');
        return new Response("search = [$search]");
    }

    // /parameters/action06?name=martin&age=42：一次性获取所有参数，以数组形式
    #[Route('/action06', name: 'action06')]
    public function action06(Request $request): JsonResponse
    {
        return $this->json($request->query->all());
    }

    // /parameters/action07?age=42&page=2：#[MapQueryParameter] 属性将
    // URL 参数绑定到同名的操作参数，并将其转换为
    // 相应的类型。没有默认值的参数是必需的
    #[Route('/action07', name: 'action07')]
    public function action07(#[MapQueryParameter] int $age, #[MapQueryParameter] int $page = 1): Response
    {
        return new Response("age = [$age], page = [$page]");
    }
}
    • 第 22 行：请求的 [query] 属性在一个参数“包”（一个 [InputBag] 对象）中包含 URL 的参数，其 [get] 方法返回某个参数的值（已解码），如果参数不存在则返回 [null] ；
    • 第 23 行：该动作显示值及其类型：函数 [get_debug_type] 返回值的类型名称。从 URL 获取的值始终是字符串（[string]）。运算符 [.] 把插值后的字符串与类型连接起来；
    • 第 32 行：[getInt] 方法读取参数并把它转换为整数。缺少的参数返回 0；不是整数的值（[abc]）会导致 400 错误（Bad Request）。类似地，还有 [getBoolean]（[1]、[true]、[on] 和 [yes] 为真）、[getString]、[getAlpha] （仅字母）、[getDigits] （仅数字）、[getEnum] （一个列表）；
    • 第 41–51 行：一个必填参数，以及区分两种可能错误的手工转换。[throw new BadRequestHttpException(message)] 以 400 响应终止操作，并附带该消息（见示例 03，其中也抛出过 404 异常）。[filter_var] 函数来自 [PHP]，配合过滤器 [FILTER_VALIDATE_INT]，返回字符串中包含的整数，如果字符串不是整数则返回 [false] ；
    • 第 58 行：[getInt] 的第二个参数是默认值，在参数缺失时使用。列表中的页码通常就是这种情况；
    • 第 67 行：并没有要求 [PHP] 变量必须与 URL 参数同名。搜索引擎经常使用一个简短的参数 [q] （query）；
    • 第 75 行：[all()] 以关联数组的形式返回 URL 的所有 参数，动作再把它转换为 JSON（见示例 03）；
    • 第 81–85 行：声明式的做法。属性 [#[MapQueryParameter]] 放在动作参数之前，把该参数与 URL 中的同名参数关联起来，并把它转换为所声明的类型（[int]）。没有默认值的参数是必填的：如果它缺失或无法转换，就会导致 404 错误（按所写的 URL 不对应任何有效页面）。默认值（[$page = 1]）使它成为可选的。这正是第 41–51 行所做的事情，只用一行就完成了。

    3.2. 示例 08：用类描述的动作模型

    动作的模型可以用一个类来描述：每个期望的参数对应一个属性及其类型，并且以属性的形式写出它必须满足的约束 。[Symfony] 随后自己根据请求创建该对象、验证它，并把它传递给动作。这些约束是 Validator 组件的类：[NotBlank] （必填）、[Length] （长度）、[Range] （区间）、[Choice] （值列表）、[Email]、[Regex]……[Symfony] 提供了七十多个这样的约束。

    <?php
// src/Model/PersonModel.php：操作的模型，一个描述
// 预期参数及其约束的类

namespace App\Model;

use Symfony\Component\Validator\Constraints as Assert;

readonly class PersonModel
{
    public function __construct(
        // 必填，然后是 2 到 20 个字符的字符串：Sequentially 按顺序检查
        // 各个约束，并在第一个不满足的约束处停止
        #[Assert\Sequentially([
            new Assert\NotBlank(),
            new Assert\Length(min: 2, max: 20),
        ])]
        public ?string $name = null,
        // 必填，0 到 150 之间的整数
        #[Assert\NotNull]
        #[Assert\Range(min: 0, max: 150)]
        public ?int $age = null,
        // 必填，仅限这三个值之一
        #[Assert\NotBlank]
        #[Assert\Choice(choices: ['Mr', 'Mme', 'Melle'])]
        public ?string $title = null,
        // 可选；如果存在，则必须是有效的电子邮件地址
        #[Assert\Email]
        public ?string $email = null,
    ) {
    }
}
    • 第 7 行：导入约束命名空间，使用短名称 [Assert]：约束将写成 [Assert\NotBlank]、[Assert\Length]……这是所有 [Symfony] 项目中的标准做法；
    • 第 9–31 行：一个不可变类，其属性由构造函数初始化（示例 03）。每个属性都有默认值 [null]，以及可空类型（[?string]、[?int]：字符串，或 [null]）：如果 URL 中缺少某个参数，该属性默认为 [null]，再由一个约束来决定它是否必填。这是编写这类类的标准方式；
    • 第 14–18 行：姓名是必填的（[NotBlank] 会拒绝 [null] 和空字符串），并且必须由 2 到 20 个字符组成（[Length]）。约束 [Sequentially] 按顺序检查它所包含的约束，并在第一个失败的约束处停止：空姓名只会产生一个错误，而不是两个。约束的参数是具名参数 （[min: 2]），这是自 [Symfony] 8 起的要求；
    • 第 20–22 行：年龄是必填的（[NotNull]），并且必须在 0 到 150 之间（[Range]）。它的类型是 [?int]：[Symfony] 会把来自 URL 的字符串转换为整数；
    • 第 24–26 行：称谓是必填的，并且必须是所列三个值之一（[Choice]）；
    • 第 28–29 行：电子邮件地址是可选的（没有 [NotBlank] 约束）；如果提供，它必须有效。除了约束 [NotBlank] 之外，其余的约束都接受 [null]：它们只验证存在的值。

    这个模型描述了期望的数据；它不包含任何验证指令。这称为声明式风格。

    <?php
// src/Controller/PersonsController.php：一个其模型为类的操作

namespace App\Controller;

use App\Model\PersonModel;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpKernel\Attribute\MapQueryString;
use Symfony\Component\Routing\Attribute\Route;

class PersonsController extends AbstractController
{
    // /persons/action01?name=martin&age=42&title=Mr
    // #[MapQueryString]：Symfony 根据 URL 的参数
    // 构建一个 PersonModel 对象，并在调用操作之前对其进行验证。无效的
    // 模型会引发异常（见 src/EventListener/ValidationErrors.php），
    // 并且操作永远不会被调用
    #[Route('/persons/action01', name: 'persons_action01', methods: ['GET'])]
    public function action01(Request $request, #[MapQueryString] PersonModel $person): JsonResponse
    {
        return $this->json([
            'received' => $request->query->all(),
            'person' => $person,
            'ageType' => get_debug_type($person->age),
        ]);
    }
}
    • 第 21 行：[#[MapQueryString]] 属性指示 [Symfony] 根据 URL 的参数构造 [$person] 参数。参数解析器（示例 05）分两步完成这项任务。首先，它进行转换：使用 Serializer，它创建一个 [PersonModel] 对象，其中每个属性接收 URL 中同名的参数，并转换为其对应的类型。然后，它对该对象进行验证：检查每个属性的每个约束。如果一切正确，就调用动作。否则，它会抛出异常（一个状态码为 404 的 [HttpException] ，其中包含一个 [ValidationFailedException]，而它本身包含所有 错误的列表，而不仅仅是第一个错误），并且永远不会调用动作：因此动作不必担心无效数据；

    谁来处理这个异常？默认情况下，是 [Symfony] 自己，通过 404 错误响应（对于 [#[MapRequestPayload]] 则是 422，示例 11）：即它的错误页面，或者对于请求 JSON 的客户端，则是一个详细列出各错误的文档。在这里，我们希望在所有情况下都返回 JSON 格式的错误响应，状态码为 400，并采用我们自己的格式。这就是监听器的作用。

// src/EventListener/ValidationErrors.php：对于整个
// 应用程序，无效的模型都会产生一个详述错误的 400 响应

namespace App\EventListener;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;
use Symfony\Component\HttpKernel\KernelEvents;
use Symfony\Component\Validator\Exception\ValidationFailedException;

// [kernel.exception] 事件的监听器，当异常
// 从操作（或其参数的准备过程）中抛出时触发
#[AsEventListener(event: KernelEvents::EXCEPTION)]
class ValidationErrors
{
    public function __invoke(ExceptionEvent $event): void
    {
        // #[MapQueryString] 引发的 HTTP 异常包含验证的异常，
        // 而后者包含错误列表（“violations”）
        $validation = $event->getThrowable()->getPrevious();
        if (! $validation instanceof ValidationFailedException) {
            return;    // 另一个异常：Symfony 照常处理
        }
        $errors = [];
        foreach ($validation->getViolations() as $violation) {
            $errors[] = ['field' => $violation->getPropertyPath(), 'message' => $violation->getMessage()];
        }
        // 事件的响应会取代 Symfony 的错误页面
        $event->setResponse(new JsonResponse(['status' => 400, 'errors' => $errors], 400));
    }
}
    • 第 15 行：[kernel.exception] 事件的监听器（常量 [KernelEvents::EXCEPTION]）。[Symfony] 会在动作执行期间或准备其参数时发生异常的情况下触发这个事件，时间在动作生成自己的错误响应之前。以这种方式声明后，监听器适用于应用中的所有 动作：每个验证模型的动作都能受益于它，而无需编写任何一行错误处理代码；
    • 第 22 行：事件是一个 [ExceptionEvent] 对象，它携带异常（[getThrowable()]）。由 [#[MapQueryString]] 抛出的异常是一个 HTTP 异常；[getPrevious()] 返回导致它的异常——即验证异常；
    • 第 23–25 行：如果不是验证错误，监听器什么也不做：[Symfony] 会照常处理该异常。运算符 [!] （非）用于反转条件；
    • 第 26–29 行：[getViolations()] 返回错误列表，这些错误被称为（约束）违规。每个违规都有一个路径（[getPropertyPath()]，即出错属性的名称）和一条消息。[$errors[] = ...] 向数组 [$errors] 的末尾添加一个元素；
    • 第 31 行：[setResponse] 向事件返回一个响应：一个状态码为 400 的 JSON 响应。[Symfony] 会发送它来取代自己的错误页面（并且和任何响应一样，它会经过监听器 [ReadableJson]）。

namespace App\Controller;

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\Routing\Attribute\Route;
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validator\ValidatorInterface;

#[Route('/arrays', name: 'arrays_', methods: ['GET'])]
class ArraysController extends AbstractController
{
    // /arrays/action01?color=red&color=green：对于 PHP，第二个参数
    // 会替换第一个：只保留最后一个值
    #[Route('/action01', name: 'action01')]

    // PHP 将所有值存储在一个数组中
    #[Route('/action02', name: 'action02')]
    public function action02(Request $request): JsonResponse
    {
        // all('color')：以数组形式表示的参数（缺失时为空）
        $colors = $request->query->all('color');
        return $this->json(['color' => $colors, 'count' => count($colors)]);
    }

    // /arrays/action03?color[]=red：一个数组，逐项验证
    #[Route('/action03', name: 'action03')]
    public function action03(Request $request, ValidatorInterface $validator): JsonResponse
    {
        $colors = $request->query->all('color');
        // 我们可以验证任何值（此处是数组），只需给出
        // 要验证的约束
        $violations = $validator->validate($colors, [
            // 至少包含一项的列表
            new Assert\Count(min: 1),
            // All：约束应用于每一项
            new Assert\All([new Assert\Choice(choices: ['red', 'green', 'blue'])]),
        ]);
        $errors = [];
        foreach ($violations as $violation) {
            $errors[] = "color{$violation->getPropertyPath()}: {$violation->getMessage()}";
        }
        return $this->json(['colors' => $colors, 'valid' => ! $errors, 'errors' => $errors]);
    }

namespace App\Binding;

use DateTimeImmutable;
use Stringable;

readonly class DayFr implements Stringable
{
    public function __construct(public DateTimeImmutable $date)
    {
    }

    // 路径文本 -> DayFr 对象；null：该文本不表示日期
    public static function fromUrl(string $text): ?self
    {
        // "!d-m-Y" 中的 ! 将时间重置为零（否则将是当前时间）
        $date = DateTimeImmutable::createFromFormat('!d-m-Y', $text);
        // createFromFormat 接受 "31-02-2026"（并将其变成 3 月 3 日）：我们检查
        // 重新格式化后的日期是否与收到的文本一致
        if ($date === false || $date->format('d-m-Y') !== $text) {
            return null;
        }
        return new self($date);
    }

    // DayFr 对象 -> 路径文本（在构建路由的 URL 时使用）
    public function __toString(): string
    {
        return $this->date->format('d-m-Y');
    }
}

    public function resolve(Request $request, ArgumentMetadata $argument): iterable

// src/Binding/DetectLanguage.php：一个为操作计算一条信息的监听器

namespace App\Binding;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\KernelEvents;

// [kernel.request] 事件：请求到达，操作尚未被调用
#[AsEventListener(event: KernelEvents::REQUEST)]
class DetectLanguage
{
    public function __invoke(RequestEvent $event): void
    {
        $request = $event->getRequest();
        // 头部 "Accept-Language: fr-FR,fr;q=0.9,en;q=0.8" -> "fr"：浏览器在所提供的语言中
        // 偏好的语言（默认为第一个）
        $language = $request->getPreferredLanguage(['fr', 'en']);
        // 请求的属性（ATTRIBUTES）：应用程序存储在那里的信息，
        // 供之后处理该请求的函数使用
        $request->attributes->set('language', $language);
    }
}
    • 第 11 行：[kernel.request] 事件的监听器，在请求到达时、调用动作之前触发（路由本身就是这个事件的一个监听器：生命周期一章将讨论它们的顺序）；
    • 第 19 行：请求的 [Accept-Language] 头部按偏好顺序指明用户的语言：[fr-FR,fr;q=0.9,en;q=0.8] （[q] 系数以 0 到 1 的刻度衡量偏好程度）。[getPreferredLanguage] 从应用所提供的语言中选出用户偏好的语言；如果没有头部，则默认取列表中的第一种语言；
    • 第 22 行：语言存放在请求的属性 中，名称为 [language]，与路由参数放在一起。

    监听器会对所有请求运行。[Symfony] 没有其他框架中那种路由中间件的等价物：只应对某些路由起作用的监听器要自己检查路由名称（[$request->attributes->get('_route')]）。至于动作，它无需做任何特殊处理就会收到这条信息（见控制器）。

// src/Binding/NoSpaceValidator.php：NoSpace 约束的检查

namespace App\Binding;

use Symfony\Component\Validator\Constraint;
use Symfony\Component\Validator\ConstraintValidator;

class NoSpaceValidator extends ConstraintValidator
{
    public function validate(mixed $value, Constraint $constraint): void
    {
        if ($value !== null && str_contains((string) $value, ' ')) {
            // 该值不合适：我们报告一个“violation”，附带
            // 约束的消息
            $this->context->buildViolation($constraint->message)->addViolation();

    }
}

// src/Model/SearchModel.php：搜索的模型

namespace App\Model;

use App\Binding\NoSpace;
use DateTimeImmutable;
use Symfony\Component\Validator\Constraints as Assert;

readonly class SearchModel
{
    public function __construct(
        // 一个“自制的”约束
        #[NoSpace]
        public ?string $keyword = null,
        // DateTime：格式为 dd/mm/yyyy 且存在的日期；{{ value }}：收到的值
        #[Assert\DateTime(format: 'd/m/Y', message: '{{ value }} is not a valid dd/mm/yyyy date')]
        public ?string $since = null,
    ) {
    }

    // 日期，转换为日期对象（缺失时为 null）
    public function since(): ?DateTimeImmutable
    {
        return $this->since === null ? null
            : DateTimeImmutable::createFromFormat('!d/m/Y', $this->since);
    }
}
    • 第 14–15 行：我们的约束，其用法与任何其他约束完全相同；

namespace App\EventListener;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;
use Symfony\Component\HttpKernel\KernelEvents;
use Symfony\Component\Validator\Exception\ValidationFailedException;

#[AsEventListener(event: KernelEvents::EXCEPTION)]
class ErrorAsText
{
    public function __invoke(ExceptionEvent $event): void
    {
        $validation = $event->getThrowable()->getPrevious();
        if ($validation instanceof ValidationFailedException) {
            $event->setResponse(new Response($validation->getViolations()[0]->getMessage(),

    }
}

namespace App\Controller;

use App\Binding\DayFr;
use App\Binding\DayFrResolver;
use App\Model\SearchModel;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\MapQueryString;
use Symfony\Component\HttpKernel\Attribute\ValueResolver;
use Symfony\Component\Routing\Attribute\Route;

#[Route('/examples', name: 'examples_', methods: ['GET'])]
class ExamplesController extends AbstractController
{
    // /examples/schedule/23-09-2026：#[ValueResolver] 将 $day 参数交给
    // DayFrResolver 解析器，由它将其绑定到 {day} 路由参数
    #[Route('/schedule/{day}', name: 'schedule', requirements: ['day' => '[0-9]{2}-[0-9]{2}-[0-9]{4}'])]
    public function schedule(#[ValueResolver(DayFrResolver::class)] DayFr $day): Response
    {
        // generateUrl 构建路由的 URL；DayFr 对象通过其 __toString 方法
        // 变成路径文本："23-09-2026"
        return new Response("schedule for the day [{$day->date->format('Y-m-d')}], of type "
            .get_debug_type($day->date).', URL: '.$this->generateUrl('examples_schedule', ['day' => $day]));
    }

    // /examples/hello：一个并非来自 URL、而是来自头部的参数，
    // 由 DetectLanguage 监听器计算并存储在请求的属性中
    #[Route('/hello', name: 'hello')]
    public function hello(string $language): Response
    {
        return new Response($language === 'en' ? 'Hello!' : 'Bonjour !');
    }

    // /examples/search?keyword=symfony&since=01/09/2026
    #[Route('/search', name: 'search')]
    public function search(#[MapQueryString] SearchModel $search): Response
    {
        $since = $search->since()?->format('Y-m-d');
        return new Response("search for [$search->keyword] since [$since]");
    }
}
    • 第 20 行：日历路由，其参数 [{day}] 受正则表达式约束：[[0-9]] 表示一个数字，[{2}] 表示重复前面的模式：两位数字、连字符、两位数字、连字符、四位数字。格式不同的路径段不会匹配该路由（404），我们的解析器根本不会被调用；
    • 第 21 行：属性 [#[ValueResolver]] 将参数 [$day] 分配给一个解析器（通过其类标识）：只有它才会提供该参数。如果没有这个属性，[Symfony] 会按优先级顺序尝试各个解析器，而路由参数解析器——其优先级高于我们的——会把字符串 ["23-09-2026"] 提供给类型为 [DayFr]的参数：这会导致错误；
    • 第 25–26 行：日期以国际格式显示（[Y-m-d]：[2026-09-23]）。[generateUrl] 方法（来自 [AbstractController] ）为命名路由及其参数创建 URL（这就是 [redirectToRoute] 在示例 04 中所做的）。传给它的是 [DayFr] 对象本身：[Symfony] 通过其 [__toString] 方法将其转换为字符串。URL 相对于站点（[/examples/...]）；若传入第三个参数，则需要绝对 URL；
    • 第 31–35 行：参数 [$language] 与任何路由参数都不对应。不过，路由参数解析器通常会查找与参数同名的请求属性：因此它找到了监听器 [DetectLanguage] 存放在那里的值。仅此而已：参数上不需要任何属性；
    • 第 38–43 行：搜索模型，与 URL 参数绑定并经过验证（示例 08）。动作只接受有效的模型；它调用日期转换方法。[?->] 运算符（nullsafe）在对象不是 [null] 时调用方法，否则返回 [null] 。

    3.6.6. 结论

    让我们总结动作获取其模型的各种方式：

    路由参数
    动作的参数，名称相同；按其类型转换（[int $id]），由 [requirements]约束；通过参数解析器与对象关联（[ValueResolverInterface]、[#[ValueResolver]]）
    URL 参数
    [$request->query->get(...)]、[getInt]、[all]……；[#[MapQueryParameter]]；重复的参数写作 [name[]]
    POST 表单中的字段
    [$request->request->get(...)]，或 [$request->getPayload()->get(...)]，后者也可以读取 JSON
    JSON 请求体
    [$request->toArray()]、[$request->getPayload()]
    由类描述的模型
    [#[MapQueryString]] （URL）、[#[MapRequestPayload]] （请求体）：先转换，再验证
    请求头
    [$request->headers->get(...)]，以及解析请求头的方法，例如 [getPreferredLanguage]
    验证
    约束（[#[Assert\...]]），在动作之前检查（[#[MapQueryString]]……）或在动作中检查（[ValidatorInterface]）；“自定义”约束（[Constraint] 和 [ConstraintValidator]）
    消息
    [default_locale] 语言、翻译器，以及 [translations/validators.xx.yaml] 字典
    常见错误
    [kernel.exception] 的事件监听器
    计算得出的参数
    [kernel.request] 事件监听器，它把信息存放在请求属性中

    另一方面，HTML 表单需要的不仅仅是验证：它们必须被显示出来，带着用户的输入和错误重新显示，并且要防范伪造请求。[Symfony] 把这一切都委托给它的 Form 组件。这是下一章的主题，届时视图已经介绍过了。
